## 1. 关于「有人做过不可怕」——差异化定位收敛

**认同用户的战略判断。** 但需精确化：

| 说法 | 是否成立 |
|---|---|
| 「餐饮供应链系统有人做过」 | ✅ 成立。天财商龙、用友好生意、简道云、猎农均有成熟产品 |
| 「所以我不该做」 | ❌ 不成立。**它们的客户是连锁**（有 IT、有财务、有专职仓管、能承受实施周期）。**没有人给"一家店、老板自己、每天 1 分钟"做过**——因为这类客户付不起实施费，市场自动放弃了他们 |

**因此本项目定位收敛为一句话：**

> **不做"小一号的 ERP"，做"第一个把内控视角带给单店老板的工具"。**

具体表现为三件别人不做的事：

| # | 别人做什么 | 我们做什么 |
|---|---|---|
| 1 | 把流程管起来（单据齐全、审批留痕） | **找出钱漏在哪**（账实差异、隐性成本、量价差异） |
| 2 | 给财务报表 | **给大白话结论**（每天要做多少才不亏） |
| 3 | 卖给 IT / 财务 | **卖给老板本人**，且只需要他每天 1 分钟 |

**判断标准（写进产品验收）**：如果某个功能让老板的每日录入时间增加超过 30 秒，砍掉它。

## 2. 架构总纲：为「未来必然要加字段」而设计

> 用户原始诉求：*"未来增加字段时，对整体数据链路不会有太大影响，调用修正逻辑比较方便，避免一个字段修改导致一堆表出现维修。"*

这是**数据库设计问题，不是产品问题**。以下 5 条纪律是答案。

### 2.1 纪律一：行化，不要列化

**反面例子（必踩的坑）**：把时段营业额建成 24 列。

```sql
-- ❌ 错误：加"天气""是否节假日"就要再加列，改到第三年这张表有 60 列
CREATE TABLE revenue_daily (
  biz_date, h0, h1, h2, ... h23   -- 24 列
);
```

**正确做法**：

```sql
-- ✅ 时间作为维度存成行
CREATE TABLE fact_hourly (
  shop_id, biz_date, hour, channel, amount, orders
);
-- 加"是否节假日" = 加一个维度表，事实表一行不动
CREATE TABLE dim_calendar (biz_date, is_holiday, is_weekend, weather, event_note);
```

**规则：任何"同一件事的多个取值"都存成行，不存成列。**
时段、渠道、品类、供应商、员工——全部行化。

---

### 2.2 纪律二：宽表 + JSON 扩展列（**不要纯 EAV**）

用户自定义字段的三种方案对比（联网查证）：

| 方案 | 加字段成本 | 查询性能 | 类型安全 | 结论 |
|---|---|---|---|---|
| 纯 EAV（entity/attribute/value 三表） | 插一行 | **差**（多表 join，报表会崩） | 弱 | ❌ 全量用会死 |
| **宽表 + JSON 扩展列** | 插一行元数据 | 好（稳定字段仍走索引） | 中 | ✅ **推荐** |
| 全部固定列（现在的做法） | **ALTER TABLE** | 最好 | 强 | ❌ 加字段就改表 |

**推荐实现：**

```sql
-- 稳定字段走固定列（查询高频、需要索引）
CREATE TABLE revenue_daily (
  id, shop_id, biz_date, amount, orders,
  ext TEXT        -- JSON：{ "dine_in": 2600, "takeout": 1200, "groupon": 400,
                  --        "weather": "雨", "is_holiday": 1, ... }
                  -- 新增字段全部塞这里，表结构永不变
);
```

**配套：字段定义注册表（元数据驱动 UI 与校验）**

```sql
CREATE TABLE field_def (
  code          TEXT PRIMARY KEY,   -- 'dine_in'
  entity        TEXT,               -- 'revenue_daily'
  label         TEXT,               -- '堂食营业额'
  data_type     TEXT,               -- number / text / date / enum
  unit          TEXT,
  is_required   INTEGER DEFAULT 0,
  default_value TEXT,
  enum_values   TEXT,               -- JSON数组，用于下拉
  sort_order    INTEGER,
  enabled       INTEGER DEFAULT 1
);
```

**加「堂食客单价」这个字段的完整流程 = 往 `field_def` 插 1 行 + 往 `metric_def` 插 1 行。不执行任何 DDL。**

SQLite 通过 JSON1 扩展支持 JSON 查询；M4 迁 PostgreSQL 后可用 JSONB + GIN 索引，性能更好。**这个迁移路径在设计时就留好了。**

> **为什么不选纯 EAV**：查证结论明确——EAV 的代价是"查询复杂、类型不安全、索引困难"。我们的场景（每天出一张报表）对查询性能敏感，全量 EAV 会让报表变慢一个数量级。**混合方案是唯一正确解。**

---

### 2.3 纪律三：**指标注册表**（本架构的核心）

> 这是解决"改一个字段导致一堆表维修"的**根本手段**。

**所有派生指标集中在一张表定义，公式以字符串存储，由计算引擎动态解析。**

```sql
CREATE TABLE metric_def (
  code          TEXT PRIMARY KEY,   -- 'labor_cost_rate'
  name          TEXT,               -- '人力成本率'
  layer         TEXT,               -- 'L1'
  unit          TEXT,               -- 'percent' / 'yuan' / 'times' / 'day'
  formula       TEXT,               -- 'labor_cost / revenue'
  depends_on    TEXT,               -- JSON数组: ["labor_cost","revenue"]
  benchmark_key TEXT,               -- 业态基准区间键
  warn_high     REAL,               -- 预警上限
  warn_low      REAL,               -- 预警下限
  higher_better INTEGER,            -- 1=越大越好（如人效） 0=越小越好
  plain_text    TEXT,               -- 大白话模板，见下
  enabled       INTEGER DEFAULT 1,
  version       INTEGER DEFAULT 1
);
```

**示例数据（加指标 = INSERT，改口径 = UPDATE，不动任何业务表）：**

| code | name | formula | 大白话模板(plain_text) |
|---|---|---|---|
| `avg_ticket` | 客单价 | `revenue / orders` | 「平均每单 {value} 元」 |
| `avg_ticket_dine` | 堂食客单价 | `revenue_dine / orders_dine` | 「堂食平均每单 {value} 元」 |
| `avg_ticket_online` | 线上客单价 | `revenue_online / orders_online` | 「外卖平均每单 {value} 元」 |
| `labor_cost_rate` | 人力成本率 | `labor_cost / revenue` | 「人工钱占营业额 {value}」 |
| `area_efficiency` | 坪效(日) | `revenue / area_sqm` | 「每平米今天产出 {value} 元」 |
| `hourly_share` | 时段占比 | `revenue_hour / revenue` | 「{hour} 点这一小时占全天 {value}」 |
| `table_turnover` | 翻台率 | `tables_served / table_count` | 「今天每张桌子翻了 {value} 次」 |
| `breakeven_daily` | 保本营业额(日) | `(rent_m + utility_m + labor_m + fixed_m) / 30 / gross_margin` | 「你每天至少要做 {value} 元才不亏」 |
| `stock_variance` | **账实差异率** | `abs(theory_usage - actual_usage) / theory_usage` | 「账面应该剩 {theory} 斤，实际 {actual} 斤，差 {value}」 |
| `cash_ccc` | 现金周转周期 | `inv_days + ar_days - ap_days` | 「从付钱进货到收回钱，要 {value} 天」 |

**这就是"修正逻辑方便"的实现方式**：口径错了，改 `metric_def.formula` 一个字符串，然后重跑一次快照任务即可。**业务表、API、前端全部不动。**

配套缓存表（派生值只读，永不作为输入）：

```sql
CREATE TABLE metric_value (
  shop_id, period_start, period_end, metric_code,
  value REAL, computed_at TEXT,
  PRIMARY KEY (shop_id, period_start, period_end, metric_code)
);
```

### 2.4 纪律四：指标三层，改动不向上冒泡

```
┌─ 原子层（只做加减，可累加）────────────────┐
│ revenue / labor_cost / purchase / waste /  │
│ rent / utility / orders / hours / tables   │
└────────────────────────────────────────────┘
                    ↓
┌─ 派生层（含除法，不可跨期相加！）──────────┐
│ 客单价 / 坪效 / 人力成本率 / 毛利率 / 翻台率 │
│ ⚠ 派生值禁止再被其他公式当作"可累加输入"    │
└────────────────────────────────────────────┘
                    ↓
┌─ 组合层（由派生值再算）────────────────────┐
│ 保本营业额 / 现金周转周期 / 综合诊断分       │
└────────────────────────────────────────────┘
```

**关键约束（必须写进代码）**：

> **派生指标禁止跨期相加。** 7 天的人力成本率 ≠ 每天人力成本率 ÷ 7，必须 `Σ人力成本 ÷ Σ营业额` 重算。

这是最常见的报表错误来源。引擎在解析 `metric_def.formula` 时，若发现分母或分子引用了派生指标，**直接拒绝并告警**。

---

### 2.5 纪律五：主数据快照 + 事实不可变 + 红冲更正

| 问题 | 解法 | 说明 |
|---|---|---|
| 供应商改了账期，历史采购单跟着变 | **主数据快照** | 单据创建时把 `term_days`、`rate`、`credit_limit` 快照进单据 |
| 单据录错了 | **事实不可变** | 禁止 UPDATE，开一张红冲单（负数量）冲销，再开新单 |
| 商品改了规格，历史出库单错乱 | **商品主数据版本化** | `goods_version` 表，单据引用 `goods_id + version` |

> 前两条是财务系统的标准做法，也是用户内控本行。**不做这个，三个月后数据就不敢信了。**

## 3. BOM / 成本卡（餐饮）：用户的理解 + 三点修正

### 3.1 用户理解正确的部分

> 用户：「BOM 只能用于测算标准成本……理论材料损耗 vs 实际损耗，这块要每天盘点称重，是执行力问题」

✅ **完全正确。** BOM 的本质就是**标准成本**，用途是做差异分析，不是做实时核算。

### 3.2 修正一：BOM 里漏了「出成率」，这是致命的

```
西红柿炒蛋的 BOM：
  鸡蛋    100 g   出成率 88%   → 实际需投 114 g 毛料
  西红柿  200 g   出成率 92%   → 实际需投 217 g 毛料
  调料    n  g    出成率 100%

出成率 = 加工后可用重量 ÷ 初加工前重量
```

**不填出成率，标准成本必然算低。** 因为采购按毛料付钱，BOM 按净料写量——毛净差就是一笔永远对不上的账。

### 3.3 修正二：差异必须拆成「量差」和「价差」

这是标准成本差异分析的标准做法（用户财务 BP 本行）：

```
量差 = (实际用量 − 标准用量) × 标准价     ← 厨房的问题（超量、浪费、偷拿）
价差 = (实际价   − 标准价) × 实际用量     ← 采购的问题（涨价、换供应商）
总差异 = 量差 + 价差
```

**为什么必须拆**：总差异 500 元，可能是"厨房浪费 500"（内部管控问题），也可能是"鸡蛋涨价 500"（外部市场问题）。**不拆就不知道该找谁。**

### 3.4 修正三：不要每天全盘——用 ABC 分类做「抽盘」

用户说"每天盘点称重是执行力问题"——对，所以需要降频：

| 品类 | 判定 | 盘点频率 | 覆盖 |
|---|---|---|---|
| **A 类** | 金额占比前 20%（肉、海鲜、油） | **每周 1 次** | 约占成本 70–80% |
| B 类 | 金额占比 20–50% | 每月 1 次 | — |
| C 类 | 金额占比后 50%（调料、干货） | 每季 1 次 | — |

**只盘 A 类就能抓住 80% 的差异。** 这是让 BOM 差异分析真正能落地的关键——否则老板第三天就放弃了。

### 3.5 BOM 表结构

```sql
CREATE TABLE bom (
  id, shop_id, dish_name, goods_id,
  std_qty_net   REAL,        -- 标准净用量（BOM 写的量）
  yield_rate    REAL,        -- 出成率，如 0.88
  std_qty_gross REAL,        -- = std_qty_net / yield_rate（自动算）
  unit          TEXT,
  version       INTEGER, effective_from TEXT
);

CREATE TABLE bom_variance (
  id, shop_id, biz_date, dish_name, goods_id,
  sold_qty      INTEGER,     -- 卖出份数
  std_usage     REAL,        -- 理论耗用 = sold_qty × std_qty_gross
  actual_usage  REAL,        -- 实际耗用 = 期初 + 入库 − 期末（盘点推算）
  qty_variance  REAL,        -- 量差 = (actual − std) × std_price
  price_variance REAL,       -- 价差 = (actual_price − std_price) × actual_usage
  abc_class     TEXT         -- A/B/C，决定盘点频率
);
```

### 4.4 ⭐ 隐性成本（**用户完全没提，但这是最有说服力的一项**）

> 查证原文：「我服务过的门店中，**有超过一半在第一次完整核算隐性成本后，发现实际净利润比他们自己估算的低了 3 到 8 个百分点**。」

| 隐性成本项 | 估算方式 | 年金额（示例） |
|---|---|---|
| 食材报损与过期 | 采购额 3%–5% | 3.6–6 万 |
| **员工餐** | 人数 × 15 元/天 × 营业天数 | 2–3 万 |
| 餐具破损与更换 | 季度采购额汇总 | 0.6–1.2 万 |
| 设备维修 | 年度维修单据汇总 | 0.5–2 万 |
| **收银差异 / 漏单** | 流水 0.3%–1% | 0.4–1.2 万 |
| 退菜报废 | 退菜记录汇总 | — |

**这一块应当做成产品的"第一张震撼报表"**：老板填完一个月数据，弹出「你以为赚了 3 万，算上隐性成本实际是 1.2 万」——**这是他从来没看过的数字**。

| 是否节假日 / 周末 | `dim_calendar` 自动 | — |
| 周边事件（展会、施工、竞品开业） | 选填备注 | 归因 |

> 没有这几个字段，营业额下滑时老板只会怪店员——**有了之后，归因才成立**。这属于用户说的"把模糊地带讨论清楚"。

## 5. 修订后的数据模型清单

| 表 | 类型 | 说明 |
|---|---|---|
| `shops` `staff` `goods` `suppliers` `channels` | 维度 | 主数据，版本化 |
| `dim_calendar` | 维度 | 日期、是否周末/节假日、天气、事件 |
| `fact_daily` | 事实（日粒度） | 营业额、成本、客单、工时、损耗 + `ext` JSON |
| `fact_hourly` | 事实（时粒度） | 时段营业额、时段客单 |
| `fact_txn` | 事实（单粒度，M3+） | 销售/采购/出入库明细 |
| `shifts` `purchases` `receipts` `scraps` `stocktakes` | 单据 | 事实不可变，红冲更正 |
| `bom` `bom_variance` | 餐饮专用 | 标准成本与差异 |
| **`field_def`** | 元数据 | 自定义字段定义 |
| **`metric_def`** | 元数据 | **指标注册表（核心）** |
| **`metric_value`** | 缓存 | 派生值，只读 |

**M1 实际建表：只建 `shops` + `fact_daily` 两张。其余 M2/M3 建。**

## 6. 修订后的阶段路线

| 阶段 | 范围 | 门禁 |
|---|---|---|
| **M0** | 人工验证，0 代码 | ≥2 家店连续 14 天主动发数据 |
| **M1** | T0 六个原子数 + `field_def` + `metric_def` + `metric_value` 三张元数据表**一起建**（这是扩展能力的地基，必须最早建） | 本人连续录 7 天；**新增一个指标只靠插表，不用改代码** ← 这条是 M1 的硬门禁 |
| **M2** | 主数据 + 毛利/损耗/应付 + 时段行化 | 建 1 家店主数据；应付账期与手工一致 |
| **M3** | 单据层 + **账实差异报表** + BOM 差异（含出成率、量价差、ABC 抽盘） | 抽盘结果与全盘误差 <10% |
| **M4** | 三大报表 + **大白话管理报表** + **隐性成本报表** + 多店 + 商业化 | ≥3 家付费留存满 1 个月 |

**M1 门禁新增的关键一条**：加一个新指标（如"堂食客单价"）必须能**只通过向 `metric_def` 插一行完成，不改任何 Python/前端代码**。做不到就是架构失败，必须返工。

## 7. 给 Trae 的施工指令（v1.0 增量）

1. v0.1 第 11 节 M1 施工单**继续有效**，但**数据模型替换为本版第 5 节**。
2. **优先级最高**：`field_def` `metric_def` `metric_value` 三张表 + 一个 `MetricEngine`（读注册表、解析 formula、递归求 depends_on、拒绝派生值被跨期累加）。**这三张表是后面所有扩展的地基，必须先建。**
3. `formula` 解析器要求：支持 `+ - * / ( )`、字段引用、字面量；**遇到除以派生指标的表达式直接抛错**。
4. 所有业务表加 `ext TEXT`（JSON）列。
5. `dim_calendar` 预生成 3 年数据（是否周末、是否法定节假日）。
6. 单据表加 `is_reversal INTEGER DEFAULT 0` 与 `reversal_of INTEGER`，支持红冲。
