### M2-1 · 补全职人力成本（月薪 / 五险 / 公积金 / 福利）

| 项 | 内容 |
|---|---|
| **目标** | 让"老板以为的人工"与"实际全口径人工"两个数都能出，且保本线用全口径 |
| **根因** | `labor_m` 是引擎注入项，从 `shifts` 现算（`server/metrics_engine.py:455`），全职月薪无处录入 |
| **锚点** | `server/seed_metrics.py:27 FIELD_SEEDS`、`:117 METRIC_SEEDS`、`:251 CORE_METRIC_CODES` |

**新增 5 个字段（走 `field_def` 插行，零 DDL）**：

| code | label | scope | unit | 说明 |
|---|---|---|---|---|
| `full_time_headcount` | 全职人数 | month | 人 | 用于算人效 |
| `full_time_monthly` | 全职月薪合计 | month | 元 | 不含社保 |
| `social_insurance_m` | 五险 | month | 元 | |
| `housing_fund_m` | 公积金 | month | 元 | |
| `welfare_m` | 福利与员工餐 | month | 元 | 含员工餐、节假日加餐 |

**新增 1 个原子量（`metric_def` 插行）**：

| code | name | layer | aggregation | scope | formula |
|---|---|---|---|---|---|
| `labor_m_full` | 全口径月人工 | atomic | **additive** | month | `labor_m + full_time_monthly + social_insurance_m + housing_fund_m + welfare_m` |

> 全部输入都是 `additive`，相加仍为 `additive` —— 符合 M2-6 的约束，不会被拦。

**改 1 个公式**：

| code | 原 formula | 新 formula |
|---|---|---|
| `breakeven_daily` | `(rent_m + utility_m + labor_m) / 30 / gross_margin` | `(rent_m + utility_m + labor_m_full) / 30 / gross_margin` |

**报告口径要求**：同时展示两个数，`labor_cost_rate` 的 `plain_text` 改为「直接人工（排班工钱）占营业额 {value}」，并在 `observations` 里给出 `labor_m_full`。**两个数的差额就是老板不知道的钱**，这句话要能在结论里说出来。

**验收命令与判据**：

```bash
$PY -m pytest tests/ -q -k "labor or breakeven"
$PY scripts/seed_3y_data.py     # 重灌后看 Y3
```

| 判据 | 期望 |
|---|---|
| Y3 `labor_m_full` | **显著大于** `labor_m`（因为多了全职月薪 + 社保等） |
| Y3 `breakeven_daily` | **高于**修改前基线 2,598.68 |
| 若某月只填 `rent_m` 未填 `full_time_monthly` | `labor_m_full` 退化为 `labor_m`（不许返回 None 或 0 导致保本线变低） |
| 字段总数 | `field_def` 由 6 → **11** |

**⚠️ P0 出口门禁**：重灌 3 年数据后，`breakeven_daily` 三年仍必须是递增的，且三年数值都高于旧基线。**若比旧基线低，说明全口径没真正进公式，返工。**

## 3. P1 · 主体功能

### M2-2 · 结论话术按区间长度分档

| 项 | 内容 |
|---|---|
| **目标** | 年度总结不再说"明天" |
| **锚点** | `server/routers/report.py:151 build_conclusion`、`server/benchmarks.py` 各 `action_*` |
| **改法** | 按 `days_span` 分三档，每档一套话术： |

| 档 | 条件 | 第三行口吻 | 第二行口吻 |
|---|---|---|---|
| 日/周 | `days_span ≤ 7` | 保持现状「明天…」 | 保持现状 |
| 月/季 | `8 ≤ days_span ≤ 90` | 「这个月先做一件事…」 | 「这段时间…」 |
| 年度 | `days_span > 90` | **「明年最先要动的是…」** | **「这一年…」** |

**验收**：

| 判据 | 期望 |
|---|---|
| 3 年区间（`days_span` 365/366）第三行 | **不得包含"明天"** |
| 7 天区间第三行 | 仍包含「明天」（不许误伤） |

> 第一条写成测试：用 366 天区间调报告，断言 `"明天" not in conclusion.lines[2]`。

### M2-3 · 报告增加趋势环比段

| 项 | 内容 |
|---|---|
| **目标** | 让"还没越线但正在冲向线"能被说出来 |
| **锚点** | `server/schemas.py:210 ReportOut`、`server/routers/report.py:237 assemble_report` |
| **改法** | `ReportOut` 新增 `trend: list[TrendItem]`；`assemble_report` 取**上一等长区间**的同名指标做对比 |

```python
class TrendItem(BaseModel):
    code: str
    name: str
    current: float | None
    previous: float | None
    delta: float | None          # 当前 - 上一期
    direction: str               # "升" / "平" / "降"
    sentence: str | None         # 大白话，如「食材占比这一年在涨（30% → 41%）」
```

**纪律（硬）**：环比**必须先 Σ 原子再算比率**，不得对日率取平均。
现有守卫 4（`metrics_engine.py:418 aggregate_atoms`）自动覆盖，但**必须补一条针对 `trend` 的测试**——这是最容易图省事写错的地方。

**验收**：

| 判据 | 期望 |
|---|---|
| Y2 vs Y1 `food_cost_rate` | `direction="升"`，`delta ≈ +0.06` |
| Y3 vs Y2 `food_cost_rate` | `direction="升"`，`delta ≈ +0.05` |
| Y3 vs Y2 `efficiency` | `direction="降"`（Y3 人效反降 19%） |
| 首期（无上一期） | `trend` 为空列表，**不报错** |

| **锚点** | `server/routers/report.py:151 build_conclusion` |
| **改法** | 当 `days_span > 90` 且 `breakeven_daily` 有环比时，追加一句： |

### M2-6 · 组合层输入约束（评审加码项）

| 项 | 内容 |
|---|---|
| **目标** | 防止 M2/M3 有人把两个比率相加（如 `food_cost_rate + labor_cost_rate`） |
| **锚点** | `server/metrics_engine.py:303 validate` |
| **改法** | 求值前检查：指标依赖中若出现 `aggregation == "ratio"` 的量，**抛异常** `RatioAsInputError` |

**注意现有合法场景**：`efficiency = revenue / hours` 中 `hours` 是 `additive`，必须放行。
判定依据是 `aggregation` 字段，**不是**"是否派生" —— 与 M1 已定的 §5-1 口径一致。

**验收（必须双向断言）**：

| 用例 | 期望 |
|---|---|
| 组合指标依赖 `food_cost_rate`（ratio） | 抛 `RatioAsInputError` |
| 组合指标依赖 `hours`（additive） | 放行 |
| 新增 `labor_m_full`（additive 相加） | 放行 |

**变异验证（必做）**：把 `labor_m_full` 的 `aggregation` 改成 `ratio`，测试必须变红；改回后复跑全绿。
按「一个不会失败的断言等于没有断言」的规矩，变异结果写进交付报告。
