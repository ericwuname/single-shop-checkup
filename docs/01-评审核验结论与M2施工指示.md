## 3. 3 年测试数据的产出（参数取自联网查证的公开行业数据）

**门店**：社区快餐·测试店A（60㎡，catering）
**曲线设计**：营业额三年涨 26%，成本涨得更快 —— 用于检验系统能否抓出「有流水没利润」

| 指标 | Y1（23-10~24-09） | Y2 | Y3 | 三年变化 |
|---|---|---|---|---|
| 营业额 | 1,360,440 | 1,622,854 | 1,717,633 | **+26.3%** |
| 客单价 | 26.00 | 28.00 | 29.00 | +11.5% |
| 食材成本率 | 30.0% `[high]` | 36.0% `[high]` | 41.0% `[high]` | **+11.0 pct** |
| 人力成本率 | 16.1% `[ok]` | 16.6% `[ok]` | 21.2% `[ok]` | +5.1 pct |
| 人效（元/工时） | 128.39 | 153.35 | **123.88** | **Y3 反降 19%** |
| **保本营业额（日）** | 1,510.71 | 1,923.02 | **2,598.68** | **+72.0%** |
| 安全边际（日均÷保本） | 2.46 倍 | 2.31 倍 | **1.81 倍** | **持续收窄** |

### 3.1 系统抓到了什么（✅ 有效）

**「营业额涨 26%，保本线涨 72%」** —— 这是本产品最有价值的输出，引擎如实算出来了。
老板看到这两个数，立刻能懂"我越做越危险"。**这是设计的胜利。**

### 3.2 系统没抓到什么（❌ 缺陷，见下节）

三个年度的结论**一字不差**：

```
Y1: 这 366 天营业额 1,360,440（日均 3,717），人工 219,150（占 16.1%），食材 407,975（占 30.0%）。
    → 食材占比偏高，快餐一般 18%–22%。
    → 明天买菜前先看一眼昨天的采购单，把囤货和当天要用的分开记。
Y2: （同句式，只换了数字）
Y3: （同句式，只换了数字）
```

食材恶化 11 个百分点、人效 Y3 反降 19%、安全边际从 2.46 倍掉到 1.81 倍——**结论零变化**。

## 4. 五个缺陷（按严重度，🔴 = M2 开工前必须修）

### 🔴 缺陷 1 · 食材成本率基准区间与行业实际不符（数据错误）

| 项 | 内容 |
|---|---|
| 现状 | `benchmarks.py` 快餐食材成本率 **18%–22%**，超过即报 `high` |
| 查证 | 塔斯汀 **35%–38%**、十尾鲜 29.9%（行业参考 **30%–40%**，被评"成本控制优异"）、社区小馆 35%–45% |
| 后果 | **所有快餐店都会被判"食材占比偏高"** → 狼来了 → 老板第三次看到就不再信预警。**这直接摧毁产品的可信度** |
| 要求 | 快餐口径改为 **28%–38%（预警 >40%）**；同时在 `benchmarks.py` 里**标注每个区间的来源**，禁止凭感觉填 |
| 验证 | 用本 3 年数据重跑：Y1 30% 应判 `ok`，Y3 41% 应判 `high` |

### 🔴 缺陷 2 · 全职月薪与五险一金无法录入（模型缺口）

| 项 | 内容 |
|---|---|
| 现状 | `labor_m` 是**引擎注入项**，从 `shifts` 现算（`metrics_engine.py:455`）。`field_def` 里没有"全职月薪""社保""公积金""员工餐""福利" |
| 后果 | 只能用"月工资 ÷（人数×8h×30天）"折算成时薪录入。**全职请假、加班、社保、员工餐全部丢失** |

**这个缺口有多大（量化）**：
- M1 算出 Y3 人力成本率 **21.2%，判 ok**
- 按查证值补上社保合规成本（人工 +25%）：**26.5%，突破 25% 预警线，判 high**

**即：M1 因为缺字段，把一个本该报警的店算成了"正常"。** 这正是用户原始需求里
「正式工/临时工、五险、公积金、福利，将人力成本明晰化」——**M1 未满足**。

| 要求 | M2 必须补 |
|---|---|
| 新增字段 | `full_time_headcount`（全职人数）、`full_time_monthly`（全职月薪合计）、`social_insurance_m`（五险）、`housing_fund_m`（公积金）、`welfare_m`（福利/员工餐） |
| 指标改名 | 现有 `labor_cost_rate` 明确为「直接工价成本率」；新增 `labor_cost_rate_full` = **全口径人力成本率** |
| 报告口径 | **同时给出两个数**，差距就是老板不知道的钱 |
| 纪律 | 全部走 `field_def` 插行 + `metric_def` 插行，**零 DDL** |

### 🟡 缺陷 3 · 年度结论还在说"明天"（时态错乱）

366 天的年度总结，第三行是「**明天**买菜前先看一眼…」。
`report.py:151 build_conclusion` 的三行模板是按"日/周"设计的，**跨到年度就失真**。

| 要求 | 按区间长度分档出话术 |
|---|---|
| ≤ 7 天 | 保持现状（明天做什么） |
| 8–90 天 | 「这个月…」「下周先做一件事…」 |
| > 90 天 | 改为**年度体检口吻**：「这一年…」「明年最先要动的是…」 |

### 🟡 缺陷 4 · 看不见趋势（只有区间判断，没有环比）

食材从 30% 涨到 41%、人效 Y3 反降 19%——**全部在"正常区间内"，系统一声不吭**。
但趋势恰恰是老板最该知道的：**"你还没越线，但你正在冲向线。"**

| 要求 | M2 新增环比能力 |
|---|---|
| 做法 | `ReportOut` 增加 `trend` 段：与上一等长区间对比，给 `升 / 平 / 降` + 变化幅度 |
| 触发话术 | 「食材占比这一年在涨（30% → 41%），照这个速度明年会到 52%」 |
| 纪律 | 环比**必须先用 Σ 原子再算比率**，不得对日率取平均（现有的守卫 4 自动覆盖） |

### 🟢 缺陷 5 · `breakeven_daily` 没有基准判断（状态为 none）

可以理解（保本额无行业标准），但**它是最重要的一个数却没有任何对照**。
建议：给一个**自比对**——「保本线这一年在涨（1,511 → 2,599 元/天，涨了 72%），而日均营业额只涨了 26%」。
