**⚠️ 跨口径问题：我第一遍做错了，这里如实记录**

任务书说「`labor_m_full` 是月口径、`revenue` 是日口径，直接相除会错」，给了两个方案并说"自行解决并写清"。

**我第一遍选了「锚点月实际营业额」当月分母**（Y3 锚点月是 9 月，淡季），算出 **28.9%** ——
与任务书判据要求的 **≈26.2%** 差了 2.4 个百分点，被 `verify_m2` 的判据抓了出来。

复盘：任务书方案 (a) 里写的 `revenue_avg` 是**区间日均营业额**（就是报告里显示的那个"日均"），
不是锚点月的日均。改用区间日均后：`37,454.6 / (4,705.84 × 30)` = **26.5%** ✅ 正好对上 docs/01 §4 缺陷 2 的 26.5%。

**最终实现**（两种任务书方案等价，我做了预算以避免"把比率当分母"）：

```
方案 (a) labor_m_full / (revenue_avg × 30)     ← 我预先把 revenue_avg × 30 注入为 revenue_m_avg
方案 (b) (labor_m_full / 30) / revenue_avg
实现     labor_m_full / revenue_m_avg          ← 三者数学同值，测试里三个都断言了
```

**为什么不把 `revenue_avg`（元/天）直接当分母**：那是个"每天多少元"的率，`aggregation` 只能是 `ratio`，
拿它做分母会被 **M2-6 的守卫**拦下。要绕过守卫就得把率标成 `additive` —— **那是为了让守卫闭嘴而撒谎**。
预乘 30 之后是**金额**，标 `additive` 是真话。

**实测**：

|---|---|---|---|
| Y1 | 16.1% | 20.1% | ok / high |
| Y2 | 16.6% | 20.6% | ok / high |
| Y3 | **21.2% → high** | **26.5% → high** | ✅ 硬判据命中 |

## 4. 施工中抓到的三个真问题

### 🔴 问题 1 · `FormulaParser.names()` 把函数名当变量（潜伏 bug，M1 就存在）

| 项 | 内容 |
|---|---|
| 现象 | 种子自检报 `种子指标 stock_variance_rate 引用了不存在的名字：['abs']` |
| 根因 | `names()` 用 `ast.walk` 收集所有 `ast.Name`，而 `abs(x)` 里的 `abs` 正是一个 `Name` 节点（函数名），于是被当成依赖变量 |
| 潜伏时间 | **M1 就有**。M1 的白名单支持 `min/max/abs/round`，但**没有任何种子指标用到**，所以一直没暴露；M3-3 第一次写出 `abs(...)` 就撞上了 |
| 修法 | 新增 `_call_func_names()`，把被调用的函数名节点 id 排除出变量集；`names()` 与 `divisor_names()` 都改 |
| 守门测试 | `test_formula_function_names_not_treated_as_variables`（断言 `names()` 只剩 a/b/c/d，且求值仍正常） |
| 教训 | **白名单里支持 ≠ 被用过**。支持了却没人用的语法分支，等于没测过 |

### 🟠 问题 2 · 跨口径口径选错（**我自己的错**，被判据抓出）

第一遍用"锚点月实际营业额"做分母 → Y3 算 28.9%，与任务书判据的 ≈26.2% 差 2.4 个百分点。
判据抓出来后复盘：任务书方案 (a) 的 `revenue_avg` 是**区间日均**。改用后 26.5% ✅。

**这条不是任务书没写清，是我读漏了"日均"两个字。** 留档提醒：**口径题要先算一遍目标值再写代码**。

### 🟡 问题 3 · Pydantic 响应模型不接受 `date → str`

`StocktakeOut.take_date: str` 而 ORM 给的是 `datetime.date`，Pydantic v2 不做隐式转换 →
`ResponseValidationError`。改成 `date` 类型即可。**三个新接口同时中招**，说明这类错误会成批出现。

### 🟠 6-3 `labor_cost_rate`（直接人工率）与基准存在口径错配

M2 已发现：系统同时支持两种录入约定。**在"全职走月薪字段"的店里，排班工钱率会掉到个位数百分比**
