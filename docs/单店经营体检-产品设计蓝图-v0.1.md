## 0. 一句话定位

**给没有电脑的小店老板，用手机 10 秒录入，当天看到「钱花在哪、哪个环节在漏」的一句话结论。**

不是 ERP，不是进销存，不是收银系统。它不替代任何现有工具，只做一件事：**把散落在四处的数据拼成一张能拍板的账。**

---

## 1. 前提修正：不是「没有电脑」，是「没有 PC」

用户原始表述「小店可能连电脑都没有」需要精确化，因为精确化结果直接决定技术选型：

| 设备 | 小店实际持有情况 | 对本项目的意义 |
|---|---|---|
| 台式机 / 笔记本 | **基本没有** | Excel 类方案不可行 ✅（用户判断正确） |
| 安卓收银一体机 | **大概率有**（客如云/美团/收钱吧的硬件本质是安卓平板） | 能装 APK，但老板不会为记账单独装一个 |
| 智能手机 | **100% 有** | ← 唯一的可靠终端 |
| 微信 | **100% 在用** | ← 唯一可靠的触达渠道 |

**结论：目标终端 = 手机浏览器（H5），不是原生 APP，不是 Excel。**

用户提出「本地 APP」这条路径本蓝图**不采用**，理由见第 3 节选型表。

## 2. 三条已被查证否定的路径（禁止走）

| 路径 | 否证依据 | 结论 |
|---|---|---|
| 对接收银系统 API 自动取营业额 | 收钱吧开放平台明确「当前未开放自助注册，请与商务联系申请注册」；美团/客如云同类；小店大量使用**个人收款码**，个人码无任何 API | 放弃自动取数，接受人工录入 |
| 微信小程序（个人主体） | 个人号**无法使用支付与插件**，风控等级极高，商业上限极低；企业号需营业执照 + 300 元/年认证费 | MVP 阶段放弃，M4 之后再评估 |
| 原生 APP（Android APK） | 老板不会为一个记账工具单独下载安装；无应用商店曝光；更新需重新分发 | 全阶段放弃 |

## 3. 产品形态选型

| 维度 | 原生 APP | 微信小程序 | **H5（推荐）** | 微信公众号/客服对话 |
|---|---|---|---|---|
| 老板上手成本 | 高（下载安装） | 低（微信内） | **低（扫码/收藏链接）** | 极低（发消息） |
| 开发者门槛 | 高 | **高（资质+审核）** | **零（部署即可访问）** | 中（需公众号资质） |
| 拍照能力 | 强 | 强 | **够用（MediaDevices）** | 强 |
| 表单交互 | 强 | 强 | **够用** | 弱（只能结构化文本） |
| 图表展示 | 强 | 强 | **强（ECharts）** | 弱 |
| 迭代速度 | 慢 | 慢（审核 1–24h） | **快（改完即生效）** | 快 |
| 推送提醒 | 强 | 强（订阅消息） | **弱** | 中（模板消息） |

**选型：H5 优先（PWA 化，可添加到手机桌面），小程序后置到 M4。**

补充决策：**M0 阶段连 H5 都不做**，先用人工验证（见第 10 节）。这是本蓝图最重要的约束——**在验证「老板愿意持续提供数据」之前，不写任何生产代码。**

## 4. 四条核心设计原则

| # | 原则 | 含义 | 违反后果 |
|---|---|---|---|
| P1 | **录入零新增动作** | 录入必须发生在老板已经在做的事里（收摊看一眼小票、给小时工转工钱），不能凭空多一个「记账」动作 | 三天后废弃 |
| P2 | **当天必须有回报** | 录完立刻给一句话结论，不是攒到月底给报表 | 无即时反馈 → 无留存 |
| P3 | **允许补录，不惩罚** | 漏记 3 天也能补，不显示「连续打卡 XX 天」这类压力设计 | 断一次就永久放弃 |
| P4 | **不替老板下结论** | 只给数字 + 区间 + 可选动作，不写「你应该裁员」 | 失去信任 |

## 5. unit 哲学的正确落地：能力分层 + 自动点亮

用户原始主张：简单管控开简单模块，精细管控开精细模块。

**本蓝图保留其精神，改变其实现方式：**

> ❌ 不让老板勾选「我要开启人力成本模块」
> ✅ 老板录什么数据，系统就自动点亮哪一层

理由：老板不知道自己该开哪个模块（他不具备做这个决策的能力）。**让数据做决策，不让人做决策。**

| 层 | 层名 | 点亮条件（自动判定） | 产出指标 | 对老板的一句话 |
|---|---|---|---|---|
| **L1** | 人力成本 | 有 ≥1 天营业额 **且** ≥1 条工时记录 | 人力成本率、人效、人均日产出 | 「你这个月人工钱占营业额的 X%」 |
| **L2** | 毛利与损耗 | L1 **且** 有 ≥1 条进货记录 | 毛利率、损耗率 | 「卖 100 块，进货吃掉 X 块，损耗吃掉 Y 块」 |
| **L3** | 峰值与排班 | L1 **且** 累计 ≥7 天营业额 **且** 有 ≥1 天分时段数据 | 分时段人效、峰值错配指数 | 「周三晚市 18–20 点，人不够；周二下午 14–16 点，人多」 |
| **L4** | 单店盈亏 | L2 **且** 已填月租金 + 水电等固定支出 | **保本营业额**、四项成本占比、净利 | 「你每天至少要做 X 元才不亏」 |

**L4 的「保本营业额」是本产品的最高价值输出**，公式：

```
保本营业额(日) = 月固定成本合计 ÷ 30 ÷ 毛利率
月固定成本 = 租金 + 水电 + 人力(按月折算) + 其他固定支出
```

这一条把「我这个月赚没赚钱」翻译成「我每天要做多少才不亏」——**这是老板真正听得懂的语言。**

## 6. 用户旅程（老板的一天）

| 时刻 | 老板在做什么 | 我们的介入 | 耗时 |
|---|---|---|---|
| 22:00 打烊 | 看收银机日结小票 | 打开收藏的链接 → **拍一张小票** → 自动识别营业额 | 10 秒 |
| 22:01 | 想起今天请了两个小时工 | 同一页面下方填「小李 18–22，老张 18–22」（或拍手写排班纸） | 20 秒 |
| 22:02 | 提交 | **立刻弹出一句话**：「今天营业额 4200，人工 224，占比 5.3%，正常」 | 0 |
| 周日晚上 | 看一眼本周 | 周报页：7 天趋势 + 1 条异常提醒 | 30 秒 |

**关键：整个流程手机竖屏单手完成，无注册、无登录（用设备本地 ID + 门店码），无强制字段。**

## 7. 数据模型（SQLite DDL）

```sql
-- 门店
CREATE TABLE shops (
  id            INTEGER PRIMARY KEY,
  name          TEXT NOT NULL,
  category      TEXT,            -- 业态，用于匹配基准区间
  area_sqm      REAL,            -- 营业面积，算坪效用
  rent_monthly  REAL,            -- 月租金
  utility_monthly REAL,          -- 月水电
  open_hour     INTEGER,         -- 营业开始小时 0-23
  close_hour    INTEGER,
  created_at    TEXT
);

-- 人员
CREATE TABLE staff (
  id           INTEGER PRIMARY KEY,
  shop_id      INTEGER NOT NULL,
  name         TEXT NOT NULL,
  emp_type     TEXT,             -- 全职 / 兼职 / 小时工
  hourly_rate  REAL,             -- 小时工价，全职可填月薪/174
  active       INTEGER DEFAULT 1
);

-- 工时记录（一行 = 一人一天）
CREATE TABLE shifts (
  id            INTEGER PRIMARY KEY,
  shop_id       INTEGER NOT NULL,
  staff_id      INTEGER,
  work_date     TEXT NOT NULL,   -- YYYY-MM-DD
  start_time    TEXT,            -- "18:00"
  end_time      TEXT,            -- "22:00"
  hours         REAL,            -- 自动算，支持跨夜
  rate_snapshot REAL,            -- 当天实际工价（节假日可改写）
  cost          REAL,            -- hours * rate_snapshot
  note          TEXT,
  source        TEXT             -- manual / photo / import
);

-- 每日营业额
CREATE TABLE revenue_daily (
  id           INTEGER PRIMARY KEY,
  shop_id      INTEGER NOT NULL,
  biz_date     TEXT NOT NULL UNIQUE,
  amount       REAL NOT NULL,
  orders       INTEGER,          -- 客单数，选填
  dine_in      REAL,             -- 堂食
  takeout      REAL,             -- 外卖
  groupon      REAL,             -- 团购
  note         TEXT,
  source       TEXT
);

-- 每日进货
CREATE TABLE purchase_daily (
  id       INTEGER PRIMARY KEY,
  shop_id  INTEGER NOT NULL,
  biz_date TEXT NOT NULL,
  amount   REAL NOT NULL,
  category TEXT,
  note     TEXT
);

-- 每日损耗
CREATE TABLE waste_daily (
  id       INTEGER PRIMARY KEY,
  shop_id  INTEGER NOT NULL,
  biz_date TEXT NOT NULL,
  amount   REAL NOT NULL,
  reason   TEXT,                 -- 过期 / 报损 / 浪费 / 丢失
  note     TEXT
);

-- 分时段营业额（L3 用）
CREATE TABLE revenue_hourly (
  id       INTEGER PRIMARY KEY,
  shop_id  INTEGER NOT NULL,
  biz_date TEXT NOT NULL,
  hour     INTEGER NOT NULL,     -- 0-23
  amount   REAL NOT NULL
);

-- 体检快照（缓存算好的结果，避免每次重算）
CREATE TABLE snapshots (
  id           INTEGER PRIMARY KEY,
  shop_id      INTEGER NOT NULL,
  period_start TEXT,
  period_end   TEXT,
  metrics_json TEXT,             -- 各指标值
  layers_json  TEXT,             -- 已点亮哪几层
  conclusion   TEXT,             -- 一句话结论
  created_at   TEXT
);
```

## 8. 指标口径字典（唯一权威定义，禁止在实现中另立口径）

| 指标 | 公式 | 单位 | 所属层 |
|---|---|---|---|
| 人力成本率 | `Σ人力成本 ÷ Σ营业额` | % | L1 |
| 人效 | `Σ营业额 ÷ Σ工时` | 元/小时 | L1 |
| 人均日产出 | `Σ营业额 ÷ 出勤人天` | 元/人天 | L1 |
| 平均小时工价 | `Σ人力成本 ÷ Σ工时` | 元/小时 | L1 |
| 毛利率 | `(Σ营业额 − Σ进货) ÷ Σ营业额` | % | L2 |
| 损耗率 | `Σ损耗 ÷ Σ进货` | % | L2 |
| 坪效 | `月营业额 ÷ 营业面积` | 元/㎡ | L2 |
| 租效比 | `月租金 ÷ 月营业额` | % | L4 |
| **保本营业额(日)** | `(月租金 + 月水电 + 月人力折算 + 其他固定) ÷ 30 ÷ 毛利率` | 元/天 | L4 |
| 峰值错配指数 | 各时段 `营业额占比` 与 `人力工时占比` 之差的绝对值求和 | — | L3 |

**口径说明（必须写进产品内提示）**：所有基准区间为行业经验值，不构成考核或税务依据；表中数据只在本地/自有服务器计算，不联网上传第三方。

| 层 | 选型 | 理由 | 成本 |
|---|---|---|---|
| 前端 | **H5 + Vue3 + Vite + Vant（移动端组件库）** + PWA manifest | 免审核免备案、手机浏览器直开、可添加到桌面、拍照够用 | 0 |

## 10. 阶段路线（门禁制：不通过不得进入下一阶段）

| 阶段 | 名称 | 交付物 | **通过门禁（硬条件）** |
|---|---|---|---|
| **M0** | 人工验证（Wizard of Oz） | **零代码**。老板微信发数据 → 开发者用现成 Excel 算 → 回一句话 | **≥2 家店连续 14 天主动发数据**，且 ≥1 家愿意付费 |
| **M1** | H5 最小闭环 | 单店、单页、营业额+工时录入、当天 3 个指标 | 开发者本人连续 7 天真实录入；3 个指标与手工 Excel 结果一致（误差 <0.01） |
| **M2** | 分层点亮 + 周报 | L1/L2 自动点亮、7 天趋势图、周报页 | 录入 3 天后 L2 自动点亮；周报数据与逐日累加一致 |

| **M4** | 多店 + 商业化 | 多门店切换、订阅付费、按需评估小程序 | ≥3 付费门店留存满 1 个月 |

### 11.5 工时计算规则（易错点，必须单测覆盖）

```python
def calc_hours(start: str, end: str) -> float:
    """支持跨夜班。start/end 格式 "HH:MM"。"""
    s = to_minutes(start); e = to_minutes(end)
    if e < s:            # 跨夜，如 22:00 -> 06:00
        e += 24 * 60
    return round((e - s) / 60, 2)
```

### 11.7 边界情况（必须处理，否则视为未完工）

| 情况 | 期望行为 |
|---|---|
| 营业额未填 | 只算工时，不给人力成本率，提示「填了营业额才能算占比」 |
| 同一天重复保存 | 覆盖，不新增记录 |
| 工时为空 | 不写入数据库，不报错 |
| 跨夜班 22:00→06:00 | 算 8 小时 |
| 只有 1 天数据 | 正常出指标，结论里提示「数据不足 7 天，仅供参考」 |
| 营业额为 0 | 不除零，指标返回 null |
