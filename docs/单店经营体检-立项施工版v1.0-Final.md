## 0. 立项摘要（一页纸）

| 项 | 内容 |
|---|---|
| **一句话** | 给没有电脑的餐饮小店老板，手机 10 秒录入，当天看到「钱花在哪、哪个环节在漏」 |
| **不做什么** | 不做小一号 ERP。不做收银、不做会员、不做营销 |
| **做什么** | ① **账实差异**（账面应该剩多少 vs 实际剩多少）② **隐性成本**（他不知道的钱）③ **大白话结论**（每天做多少才不亏） |
| **目标客户** | 1–3 家店的夫妻店 / 单店老板，无 PC，有手机 |
| **M0 成本** | **0 元**（零代码，微信 + 现成 Excel） |
| **M1 成本** | **0 元**（本机 localhost，全部开源组件） |
| **最大风险** | 老板不会持续提供数据 ← **M0 存在的唯一目的就是验证这条** |
| **次要风险** | 开发者自己半途而废 ← 用「本人连续录 7 天」当门禁来防 |

## 1. M0 执行包（餐饮）—— 本周就能开始，零代码

### 1.1 找 2–3 家店

| 来源 | 说明 |
|---|---|
| 喜洋洋 | 已有关系，国庆干过，最优先 |
| 家附近的小吃店 / 快餐店 / 面馆 | 每天路过、老板面熟的 |
| 之前兼职过的店 | 有信任基础 |

**筛选标准**：老板本人常在店里、愿意聊、日营业额 2000–8000 元。**不要找连锁，不要找太忙的店。**

### 1.2 开场话术（照抄，别改）

> 「X 老板，我最近在做一个东西，帮小店算清楚一个月到底赚多少。
> 我不要你钱，也不要你装软件。**你每天打烊后微信发我三个数就行**：今天营业额多少、今天买了多少菜、今天几个人上了多久班。
> 我每周给你回一张表，告诉你人工占多少、食材占多少、跟同行比是高是低。
> **先试两周，你觉得没用就停。**」

关键点：
- **不提"系统""软件""数字化"** —— 这三个词会让老板警惕
- **明确说"不要钱"** —— 降低防备
- **明确说"两周就停"** —— 降低承诺压力
- **说清楚你要什么**（三个数）—— 让他知道成本有多低

### 1.3 每天要他发什么（一句话，10 秒）

```
今天：营业额 4200，买菜 1100，小李 18-22，老张 18-22
```

**只这三个数。多一个都不要。** 老板发语音也行，你听完自己记。

### 1.4 你每天回什么（一句话模板）

```
今天营业额 4200，人工 224（占 5.3%），食材 1100（占 26.2%）。
人工正常；食材占比偏高，快餐一般 18%–22%，
明天留意一下是买多了还是损耗多了。
```

**要求**：
- **当天回**，不超过 2 小时
- **只有三行**，第一行数字，第二行判断，第三行一个动作
- **绝不出现财务术语**（变动成本、边际贡献、保本点——全部禁掉）

### 1.5 14 天时间表

| 天 | 你做什么 | 观察什么 |
|---|---|---|
| D1–D2 | 谈 3 家，加上微信 | 几家愿意试 |
| D3–D5 | 每天收数、当天回 | **是他主动发，还是你要他才发** ← 最关键 |
| D6–D9 | 继续收；第 7 天给第一张周汇总表 | 他看了吗？有反应吗？ |
| D10–D12 | 继续收；问一句「这个对你有用吗」 | **他的原话，不要你自己判断** |
| D13–D14 | 给第二张周汇总 + 试探付费 | **愿不愿意付 99 元/月** |

### 1.6 你要自己记的（这是 M0 的真正产出）

用一张简单的表，每天记：

| 日期 | 店名 | 他主动发了吗 | 发了几项 | 他有没有追问 | 备注 |
|---|---|---|---|---|---|
| | | 是/否 | 1–3 | 有/无 | |

### 1.7 M0 门禁（不通过，M1 一行代码都不写）

> **≥2 家店连续 14 天主动发数据（不是你催出来的），且 ≥1 家明确表示愿意付费。**

**"主动发"是硬指标。** 你催出来的不算——催出来的数据，产品上线后一样要你去催，那就不是产品是外包。

## 2. 技术栈锁定（含 LLM 选型）

### 2.1 开发模型：**GLM-4.6**（智谱）

| 模型 | 编码能力 | 成本 | 中文 | 结论 |
|---|---|---|---|---|
| **GLM-4.6** | **S 级**（与 Claude Sonnet 4.6、GPT-5 Codex 同级） | **$0.50 / $2.10 每百万 token**（Sonnet 的 15%） | 好 | ✅ **首选** |
| Claude Sonnet 4.6 | S 级 | $3 / $15 | 中 | 贵 7 倍，不值 |
| GPT-5 Codex | S 级 | $2.5 / $10 | 中 | 贵 5 倍 |
| Gemini Pro | **B 级**（仅够常规任务） | $30 价格指数 | 弱 | ❌ 且有"长上下文中间丢失"问题 |
| DeepSeek V4 Pro | 68–71% SWE-bench | 价格指数 15 | 好 | 备选 |
| Qwen3.7-Max | ~63% SWE-bench | 价格指数 20 | **最好** | 备选（中文项目） |

1. **实测进 S 级**，任务正确率与 Sonnet 同级，成本只有 15%
2. 中文项目适配好（价格指数 5，全场最低）
3. **你已有智谱 key 且赠送大量 token** —— 边际成本 ≈ 0

**配置**：


### 2.2 产品内嵌模型（M3 拍照识别）：**GLM-4V**，不要用 Gemini

> **修正声明**：v1.0 第 9 节曾建议 Gemini。查证后**该建议错误**，以本节为准。

| 中文 OCR 实测（字段级） | 准确率 |
|---|---|
| **GLM-4V** | **98.7%** |
| GPT-4-turbo | 95.8% |
| Gemini | 94.5% |

| 分项 | GLM-4V |
|---|---|
| 印刷体（收银小票） | 98.2% |
| **手写体（排班纸）** | **92.7%** ← 关键，排班纸大多是手写的 |
| 复杂背景适应 | 94.5% |
| 表格结构还原 | 88.3% |

**关键特性**：原生支持 1120×1120 高分辨率输入（中文小字识别的前提）、支持 JSON 结构化输出、价格 ¥0.5–4/百万 token（**一张小票约 0.001 元**）。

**配置**：`model = glm-4v`（或 `glm-4v-flash` 若上线）

### 2.3 模型调用必须走抽象层（工程硬约束）

```python
# server/llm.py —— 禁止在任何业务代码里直接写厂商 SDK
class LLMProvider:
    def __init__(self, provider: str, model: str, api_key: str, base_url: str): ...
    def chat(self, messages) -> str: ...
    def vision(self, image_path, prompt) -> dict: ...
```

**理由**：和指标注册表同一哲学——换模型只改配置，不改业务代码。明年出现更好的模型时，成本 = 改一行配置。

### 3.3 三张元数据表（**M1 必须建，这是扩展能力的地基**）

```sql
CREATE TABLE field_def (
  code TEXT PRIMARY KEY, entity TEXT, label TEXT,
  data_type TEXT, unit TEXT, is_required INTEGER DEFAULT 0,
  default_value TEXT, enum_values TEXT, sort_order INTEGER,
  enabled INTEGER DEFAULT 1
);

CREATE TABLE metric_def (
  code TEXT PRIMARY KEY, name TEXT, layer TEXT, unit TEXT,
  formula TEXT, depends_on TEXT, benchmark_key TEXT,
  warn_high REAL, warn_low REAL, higher_better INTEGER,
  plain_text TEXT, enabled INTEGER DEFAULT 1, version INTEGER DEFAULT 1
);

CREATE TABLE metric_value (
  shop_id INTEGER, period_start TEXT, period_end TEXT,
  metric_code TEXT, value REAL, computed_at TEXT,
  PRIMARY KEY (shop_id, period_start, period_end, metric_code)
);
```

### 3.4 M1 种子指标（写进 `seed_metrics.py`）

| code | name | formula | plain_text |
|---|---|---|---|
| `labor_cost_rate` | 人力成本率 | `labor_cost / revenue` | 「人工占营业额 {value}」 |
| `efficiency` | 人效 | `revenue / hours` | 「每投一小时换回 {value} 元」 |
| `avg_ticket` | 客单价 | `revenue / orders` | 「平均每单 {value} 元」 |
| `food_cost_rate` | 食材成本率 | `purchase / revenue` | 「食材吃掉 {value}」 |
| `breakeven_daily` | 保本营业额(日) | `(rent_m + utility_m + labor_m) / 30 / gross_margin` | 「你每天至少要做 {value} 元才不亏」 |

**M1 只上这 5 个。后面加指标 = 插一行，不改代码。**

### 3.5 MetricsEngine 规格（最关键的一块）

```python
class MetricsEngine:
    def compute(self, shop_id, start, end) -> dict:
        # 1. 从 fact_daily 聚合原子值（SUM，不是 AVG）
        # 2. 读 metric_def 里所有 enabled 的指标
        # 3. 拓扑排序 depends_on，按依赖顺序求值
        # 4. 写 metric_value 缓存
        # 5. 返回 {code: value}
```

**必须实现的守卫（写单测）**：

| 守卫 | 行为 |
|---|---|
| 分母为 0 或缺失 | 返回 None，不报错、不算成 0 |
| 公式引用了派生指标做分母 | **抛异常** `DerivedMetricAsDivisorError` |
| 公式引用了不存在的字段 | 抛异常 `UnknownFieldError` |
| 跨期聚合 | 先 `Σ原子`，再算比率；**禁止对比率取平均** |

### 3.6 边界情况（必须处理）

| 情况 | 期望 |
|---|---|
| 营业额未填 | 只算工时，人力成本率返回 None，提示「填了营业额才能算占比」 |
| 同一天重复保存 | 覆盖，不新增 |
| 工时为空 | 不写入，不报错 |
| 跨夜班 22:00→06:00 | 算 8 小时 |
| 营业额为 0 | 不除零 |
| 只有 1 天数据 | 出指标，结论加「数据不足 7 天，仅供参考」 |
