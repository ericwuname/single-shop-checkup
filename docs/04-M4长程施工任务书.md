## 2. M4-3 · 存货分类体系（用户新需求，本轮重头）

### 2.1 设计原则（先讲清楚，否则会做成灾难）

| 原则 | 说明 |
|---|---|
| **只拆两级，不拆三级** | 用户说"拆一两层"。**三级分类对夫妻店是灾难**——店员是 0 意识，选不动 |
| **分类是下拉选项，不是录入负担** | 预置齐全，但**只显示用过的**。老板不用为没卖过的东西建分类 |
| **分类必须能出"成本结构表"** | 分类的价值不在好看，在能回答"我这一年肉花了多少、菜花了多少、哪个在涨" |
| **支持老板自定义二级** | 预置覆盖 80%，剩下的让他加 |
| **编码不写死供应商** | 供应商会换，写进编码就是给自己埋雷 |
| **不在编码里写死门店** | 门店间共用一套分类主数据 |

## 2bis · 商品主数据补充（用户 2026-10-16 追加：规格 / 单位 / 查重）

> 用户原话：「同一物料有不同规格要区分」「单位系数转换避免人工录错」「相似或别名的物料要弹窗校验，避免一物多码」。
> 这三件**是同一件事的三面**——都属于商品主数据治理。查证依据见 §2bis.5。

### 2bis.1 规格型号（SKU 层）

**核心规则：一个物料 = 一个编码 + 一个规格。同名不同规格必须拆开。**

| 场景 | 处理 |
|---|---|
| 大豆油 5L / 大豆油 20L | **两个编码**（规格不同就是两个 SKU） |
| 可乐 330ml 罐 / 可乐 2L 瓶 | **两个编码** |
| 番茄 / 西红柿 | **一个编码**，另一个进别名表 |

`goods` 表新增列：`spec`（规格型号文本，如"5L/桶"）、`spec_code`（规格码）、`barcode`（不同规格可有不同条码）。

**命名规范**（写进系统提示）：`名称 + 规格 + 单位`，例「大豆油 5L/桶」。
**编码规则**：`[大类]-[中类]-[序号]-[规格两位]`，商品编码控制在 8–12 位。

### 2bis.2 单位与换算（三单位制，避免人工录错）

> 查证：「按箱采购、按盒配货、按件零售，同一种商品在采购表叫箱、仓库表叫盒、销售表叫件，
> 库存差异会被误认为丢货。」

**每个品维护三个单位 + 换算系数**：

| 单位 | 用途 | 例（大豆油） |
|---|---|---|
| `purchase_unit` 进货单位 | 验收单录入用 | 箱 |
| `stock_unit` 库存单位（**基准单位**） | 库存账、成本核算 | L |
| `usage_unit` 领用单位 | 后厨领料用 | 勺 / 份 |

**换算**：`purchase_to_stock`（1 箱 = 20 L）、`stock_to_usage`（1 L = 50 勺）。

**五条硬规则**（查证）：
1. **人只接触自己环节的单位，机器负责折算** —— 验收录"箱"，库存自动折"L"，领料按"勺"扣
2. **固定换算 vs 浮动换算必须分开**：标准包装用固定换算；**散装/称重品必须强制录实重**，不接受默认换算（"把包装上的固定单位当实际重量"是高频错因）
3. **基准单位选"最稳定、最常用于核算"的，不是最小的** —— 选太大拆零全是小数，选太小人人要换算
4. **换算系数变更必须留痕** —— 供应商改包装是高频事件，改了不记就对不上账
5. **不同规格可有不同条码**，扫码时系统必须知道扫到的是哪个单位

`goods` 表新增：`purchase_unit` `stock_unit` `usage_unit` `purchase_to_stock` `stock_to_usage` `is_weighed`（是否称重品）。

### 2bis.3 查重与合并（一物多码治理，用户重点）

**查证的三步法，本产品照做**：

| 步 | 做法 | 实现 |
|---|---|---|
| 1 | **模糊匹配找疑似重复** | 名称相似度 + 规格组合 + 属性组合，阈值可配（建议 60%–100%，默认 75%） |
| 2 | **人工确认后合并** | 选一个主编码，其余**停用 + 建别名关系指向主编码**，历史数据通过别名自动归集 |
| 3 | **创建前强制查重**（用户要的弹窗） | 新建时强制填名称 + 规格 → 系统搜已有编码 → 弹窗列出疑似项与相似度 → **创建人必须点"确认不是重复"才能提交** |

**弹窗内容**：疑似物料列表 + 相似度 + 规格对比 + 两个按钮「复用已有的」/「确认新建（不重复）」。

**三条配套（用户没提但没有这三条查重就白做）**：

| # | 配套 | 为什么 |
|---|---|---|
| 1 | **合并功能** | 只提醒不合并 = 发现了也修不了。**查重和合并必须成对做** |
| 2 | **别名表** | 「番茄=西红柿」这类异名同物，靠相似度查不出来，必须显式维护别名 |
| 3 | **权限收口** | 查证：「商品编码创建权限只开放给一个角色，采购和运营只能提交申请」。否则店长随手新建，重复永远清不完 |

**🔴 一条红线（写进代码，不可绕过）**：

> **编码一旦被业务数据引用，就永不修改，只能停用后新建。**
> 直接改编码会让历史订单、库存流水里的旧编码变成孤儿数据，所有按编码聚合的报表断裂，且**不可逆**。

### 2bis.4 我补充的 7 项（你没提，但同样要命）

| # | 项 | 说明 |
|---|---|---|
| 1 | **拼音 / 首字母检索** | "k l" 找到"可乐"。中文输入慢，一线会在系统里找不到料就自己新建一个——这是一物多码的**头号成因** |
| 2 | **图片** | 避免"名字一样但东西不一样"。建档时可选传图，列表里显示缩略图 |
| 3 | **停用 ≠ 删除** | 删除会断历史。**只停用**：不允许新单选择，历史数据保留可查 |
| 4 | **一物多供应商 + 主供应商** | 同一个品多家供，需要一个默认供应商，否则采购单每次都要选 |
| 5 | **版本管理** | 微小改动（换供应商、规格微调）**不生成新编码**，用版本号区分。否则冗余编码爆炸 |
| 6 | **盘点混合单位** | 现场常见"12 箱 3 盒 5 件"。盘点要支持分别录多个单位，系统统一折算 |
| 7 | **是否称重品标志 + 强制实重** | 生鲜按重量，验收端**必须录实际净重**，不接受默认换算 |

### 2bis.5 查证依据（本节的来源）

| 结论 | 来源 |
|---|---|
| 一物多码三步法（模糊匹配 → 合并 → 创建前查重） | 九数云 / 三品 PLM / ERPNext 实践 |
| 查重上线后一物多码发生率 **18% → 2% 以下** | 三品 PLM 实测 |
| 物料数据准确率 **72% → 98%**，库存盘点准确率提升 15–20 pct | 三品 PLM 实测 |
| 某 5 门店快餐品牌清出重复品项 **约 120 个（占档案一成多）**，**盘点差异率掉了近一半** | 搭贝餐饮实施记录 |
| 单位错位导致的月度差异金额 **从数千元降到百元以内**（上线 2 个月） | 搭贝餐饮统计 |
| 三单位制（进货 / 库存 / 领用）+ 换算系数 | 简道云、企雀、用友 |
| 固定换算 vs 浮动换算；称重品强制实重 | 用友、企雀 |
| 编码永不修改只停用（改了历史变孤儿且不可逆） | 九数云、ERPNext |

## 3. M4-4 · 解锁 `purchases` / `receipts`（解 6-2）

| 项 | 内容 |
|---|---|
| **目标** | `账面库存 = 上期结存 + 入库 − 出库` 能自动算，差异才等于"跑冒滴漏" |

**关键**：分类建好才有入库单（入库必须选分类、选商品、填数量与换算）。M4-3 与 M4-4 必须一起做。

**验收**：`stock_variance` 的 `book_qty` 由系统算出（不再靠老板填），且与"老板自报"能并列对照。

## 4. M4-6 / M4-7 · 多店（用户新需求）

### 4.1 数据模型（**不加表，只加列**）

| 改动 | 说明 |
|---|---|
| `shops` 加 `owner_key` | 同一老板/同一法人的标识。M1 的 shops 是平的，加一列即可 |
| `shops` 加 `is_active` | 关店的不进汇总 |

### 4.2 汇总规则（架构天然支持，但必须测试钉死）

> **金额可加，比率不可加。** 守卫 4（`metrics_engine.py` 先 Σ 原子再算比率）已经覆盖，
> 但**必须补一条多店汇总的测试**——这是最容易被"图省事对各店比率取平均"写错的地方。

| 场景 | 正确 | 错误 |
|---|---|---|
| 3 家店总营业额 | Σ 三店营业额 | — |
| 3 家店人力成本率 | `Σ人工 ÷ Σ营业额` | ❌ 三店比率 ÷ 3 |

### 4.3 视图要求

| 视图 | 内容 |
|---|---|
| **单店** | 现状不变（切换门店） |
| **全部店（汇总）** | 总营业额、总成本、保本线、总利润；指标一律**重算**不平均 |
| **门店对比** | 各店并排，同一指标横向排名；**最好/最差各提示一家** |
| **异常汇总** | 跨店异常清单，按金额降序（老板先看最贵的那个） |

### 4.4 验收

| 判据 | 期望 |
|---|---|
| 三家店营业额 100/300/500、人工 25/60/100 | 汇总人力成本率 = **185/900 = 20.56%** |
| 同上若写成三店比率平均 | （25%+20%+20%）/3 = 21.67% → **测试必须断言远离这个值** |
| 门店对比 | 能标出"人力成本率最高的是 X 店" |

## 5. M4-8 / M4-9 · 报表视觉（用户新需求）

### 5.1 设计原则

| 原则 | 说明 |
|---|---|
| **一屏一结论** | 老板不滚动。结论永远在最上面，字号最大 |
| **颜色只用红/黄/绿** | 禁止彩虹色。颜色是信号不是装饰 |
| **数字比表格重要** | 手机上看表格是灾难。能用一行字说清就不用表 |
| **"你的位置"要看得见** | 比"偏高"两个字直观得多 |
| **异常按金额排序** | 老板先看钱最多的那个 |

### 5.2 指标卡改造（核心视觉件）

现状：指标名 + 数字 + "偏高/正常" 文字。
**改为：指标名 + 大数字 + 区间条（带你的位置指针）+ 一句话。**

```
┌────────────────────────────────────┐
│ 食材成本率                          │
│                                    │
│  41.0%                             │   ← 24px 大字
│                                    │
│  正常 ├────[██████●────────]──┤ 偏高 │   ← 区间条 + 指针
│      28%                      38%   │
│                                    │
│  食材占比偏高。                      │   ← 13px 灰字
└────────────────────────────────────┘
```

**区间条的画法**：灰底横条 → 中段绿区（low~high）→ 你的位置画一个圆点 → 越界时圆点变红并贴边。
无基准的指标（如保本额）**不画条**，只给数字。

### 5.3 报告页四段结构

| 段 | 内容 | 高度 |
|---|---|---|
| ① 结论区（顶部） | 三行大字：数字 / 判断 / 动作 | 首屏内 |
| ② 指标卡网格 | 2 列网格，每张卡如上 | 可滚 |
| ③ 趋势 | 近 12 个月折线（营业额 vs 保本线两条） | 可滚 |
| ④ 异常清单 | 按金额降序，红黄绿小标 | 可滚 |

### 5.4 验收

| 判据 | 期望 |
|---|---|
| 手机视口（375px） | 结论三行**不滚动可见** |
| 有基准的指标 | 都画出区间条与指针 |
| 无基准的指标 | 不画条，不报错 |
| 异常清单 | 按金额降序，第一条是金额最大的 |
| 颜色 | 全页只出现红/黄/绿（+ 中性灰），**不出现第四种强调色** |

## 8. 禁止事项
