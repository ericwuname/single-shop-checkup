## 1. 全景：一个产品，三个档位

你提的需求是对的：小店老板和 10–20 家连锁的运营负责人，要的数据粒度完全不同。**但不应做成两个产品，而应做成同一套数据底座上的三个"档位"。**

| 档位 | 谁用 | 录什么 | 看什么 | 现状 |
|---|---|---|---|---|
| **基础档** | 夫妻店、一人店 | 营业额、买菜、今天谁上班（10 秒） | 三句话：高不高、为什么、明天做一件事 | **已有后端；M7 重做界面** |
| **进阶档** | 想看清毛利的单店 | + 分品类采购、盘点、报损、供应商欠款 | 品类成本率、理论 vs 实际用料差异、应付账款 | **后端 18 张表 / 47 个接口已有，缺界面和开关** |
| **连锁档** | 10–20 家店的运营/财务 | + POS 导入、多店、角色 | 多店横向对比、异常店排名、区域汇总 | **只有 `portfolio` 对比接口；缺导入、账号、权限、Postgres** |

### 1.1 档位怎么落地（路线图，不是现在做）

最小改动：`shops` 加 `level`（basic/advanced/chain），`field_def` 与 `metric_def` 各加 `min_level` 列。接口 `/api/meta/fields` 按店的档位过滤，前端**元数据驱动渲染**——档位升级不改前端代码，只改数据。`db.py` 的 `migrate_add_columns` 已支持加列，**不需要新表**。

| 里程碑 | 内容 | 前置条件（缺一不做） |
|---|---|---|
| M8 进阶档 | 档位列 + 采购/盘点/报损三屏（沿用设计令牌）| M0 过关，且**有真实老板主动问"能不能看得更细"** |
| M9 导入 | 常见 POS 导出文件（先 Excel/CSV）映射导入 | 手里有 ≥1 个真实 POS 导出样本。**没有样本不许设计导入格式** |
| M10 连锁 | 账号、角色（老板/店长/财务）、审计日志、Postgres、多店对比界面 | 有愿意付费的连锁客户做设计伙伴 |

**我的判断**：连锁档是最大的坑。10–20 家店的客户通常已经有 POS 和进销存，他们要的不是"又一个录入工具"，而是**把已有系统的数据拉过来对比**。所以 M9（导入）比 M8 更关键，而且没有真实样本之前做的所有设计都是猜。**现在能做的最有价值的事，是找到 1 家连锁、拿到他们的 POS 导出样本。**

## 2. 部署：域名与上线路径决策树

### 2.1 先回答你最担心的：`qiyuan.beauty` 会被影响吗？

门户 `qiyuan-portal` 是 Next.js 部署在 Vercel。**加新服务不会影响它，前提是你不去改根域名的 DNS 记录。** 新服务用**子域名**（例如 `checkup.qiyuan.beauty`），只是在 DNS 里**新增**一条记录，门户那条记录不动。

> **我没核实的**：`qiyuan.beauty` 的 DNS 现在托管在哪（Vercel / 注册商 / Cloudflare）。这决定下面走哪条路。**请你登录域名注册商后台看"DNS 服务器（nameserver）"一栏**，对照下表。

### 2.2 决策树

```
你只是想自己先在手机上试用（M7 目标）？
├─ 是 → 路径 A（同 Wi-Fi）或 路径 C（Tailscale）。  不需要域名，不碰 qiyuan.beauty。
└─ 要给别人（老板）用？
    ├─ DNS 在 Cloudflare 上 → 路径 B：Cloudflare Tunnel + 子域名（加一条记录，不影响门户）
    ├─ DNS 在 Vercel / 注册商 → 两个选择：
    │     ① 在现有 DNS 面板里给子域名加一条 CNAME 指向隧道/服务（需该服务支持）
    │     ② 把整个域名的 DNS 迁到 Cloudflare（要重新核对门户记录，有风险，不建议现在做）
    └─ 不确定 → 先用路径 A/C，等 M0 有人愿意用了再回来处理
```

### 2.3 三条路径对比（手册 `M7-手机试用手册.md` 以此为准）

| | A. 同一 Wi-Fi | B. Cloudflare Tunnel | C. Tailscale |
|---|---|---|---|
| 成本 | 0 | 隧道本身 0；要域名 | 个人用免费（**未核实当前额度，以官网为准**） |
| 暴露公网 | 否 | **是** → 必须先过 WP-1 | 否（仅你的设备组网） |
| HTTPS（装成完整 PWA 需要） | 否，通常只能"添加快捷方式" | 是 | 视配置而定（**未核实**） |
| 电脑关机/休眠 | 手机连不上 | 连不上 | 连不上 |
| 给老板用 | 否 | 可以 | 否（每个人都要装客户端） |
| 适合 | 今晚就想看一眼界面 | 正式试点 | 自己长期试用、不想暴露公网 |

**共同的硬伤：服务跑在你的 Windows 电脑上。** 电脑睡眠、断电、家里宽带换 IP / 没有公网 IP，服务就断。对"自己试用"可以接受；**对"给老板用"不可接受**——老板某天打烊记不上，就会觉得产品不可靠，然后永远不再打开。进入 M0 之前，必须决定一个常开的承载（见 §3 成本表）。

## 4. 安卓与分发的判断

- **PWA 优先。** M7 的 WP-4 让它能"添加到主屏幕"，有图标、全屏、断网可打开。对你自己试用，体验和 APK 几乎一样。
- **完整 PWA 安装需要 HTTPS。** 纯 `http://192.168.x.x` 下通常只能加快捷方式。要完整体验走路径 B（Cloudflare Tunnel）或 C（视配置）。
- **APK（WP-6）= Capacitor 云端打包**：用 GitHub Actions 编译，你本机不用装 Android SDK。我在本评审环境里没有 Android SDK、也连不上 Google 服务器，**没法替你打包验证**，所以 WP-6 只验收工作流文件的正确性，能否安装运行由你实测。
- **何时才值得做 APK**：当你确认需要**本地定时提醒**（留存功能）时。在此之前，APK 不比 PWA 多带来什么。
- **给老板的分发**：微信里发链接 / 二维码。不要一上来就让老板装 APK。

## 6. 给作者的话（不是技术）

你在这个项目上最大的优势其实不是代码，而是你**有一个已经做完、能跑、对得上账的后端**。最容易再次发生的事，是上一轮你自己总结的：**讨论热火朝天，交付差强人意**。所以我把 M7 收得很窄：

1. 先让后端安全（半天）；
2. 修两个会让老板觉得"这东西怪怪的"的文字问题（2 小时）；
3. 把界面做成你已经认可的样子；
4. 让你**自己**用 7 天。

7 天后的数据比这里所有的设计都有价值。如果那 7 天你发现自己都不想打开它，这本身就是最重要的结论——它比再做 3 个里程碑更便宜地告诉你该不该继续。
